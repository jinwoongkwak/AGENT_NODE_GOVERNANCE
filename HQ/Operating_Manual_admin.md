# 관리자-운영-매뉴얼

## overview

관리자는 연구 목적·우선순위·성공 기준과 위임 밖의 결정을 맡습니다. Agent는 승인된 범위의 실행·검증·기록을 맡고, 다음 사람이 읽어도 상태를 알 수 있게 남깁니다.

## 회사-작동-원리

| 순서 | 관리자 | Agent | 남는 것 |
|---|---|---|---|
| 1 요청 | 목표·완료 기준·대상·제약 전달 | TaskNote로 정리하고 기존 권한 확인 | 작업 계약 |
| 2 준비 | 미정인 연구 선택만 결정 | 원 증거·범위·백업·의존성 확인 | 계획과 필요한 결정 |
| 3 실행 | 필요한 위험도 2 행위를 승인 | 승인된 범위만 실행 | 파일·로그·변경 기록 |
| 4 검증 | 주장·trade-off 등 사람 판단 | 완료 기준과 실제 결과 대조 | 검증 근거·한계 |
| 5 마무리 | 검토가 필요하면 확인 | STATUS·Decisions 반영, 작업 종료 | 다음 행동이 명확한 상태 |

기본 모드는 Agent 한 명과 TaskNote로 운영합니다. 확장 모드는 같은 흐름의 계획·평가·실행을 분리하고 교환 기록을 추가하지만, Router가 구현·시험되기 전에는 활성화하지 않습니다.

## 일을-맡기는-방법

| 원하는 일 | 요청 예시 | 결과 |
|---|---|---|
| 분석만 | “이 설계의 가정과 위험을 검토하고 근거를 정리해줘.” | 분석·기록, 실제 설계 변경 없음 |
| 범위 내 수정 | “이 노트의 링크를 고치고 깨진 링크가 없는지 확인해줘.” | 백업·수정·검증 |
| 계획만 | “초안: 이 폴더를 재구성할 선택지와 파일별 대응표를 만들어줘.” | 계획과 결정 대기 |
| 승인한 실행 | “이 계획 V1.0.0대로 실행해. 대상은 이 목록이고 다른 파일은 유지해.” | 권한·백업 확인 후 실행 |
| 조건부 실행 | “내 검토가 끝나면 옮길 거야.” | 조건 충족 전 이동하지 않음 |

특정 명령 문법은 편의 기능입니다. 대상·범위·행위가 명확한 대화도 유효한 지시입니다. [승인 규칙](Commands_and_Approval_admin.md#승인과-실행-지시)에 따라 승인과 실행 권한을 기록하며, 이미 허락한 것을 반복해서 묻지 않습니다.

## 상태를-확인하는-방법

| 궁금한 것 | 볼 곳 | 읽는 법 |
|---|---|---|
| 지금 내가 할 일 | HQ 행동 뷰 | `decide`: 선택, `dispatch`: 실행 지시, `review`: 결과 확인 |
| 한 작업의 상태 | TaskNote의 현재 상태·기록 | 다음 담당·막힘·근거 확인 |
| 회사의 우선순위 | 프로젝트 색인·각 STATUS | 현재 사실과 다음 결과 확인 |
| 왜 이 결정을 했나 | Decisions | 선택지·근거·재검토 조건 확인 |
| AI가 어디까지 할 수 있나 | 작업 계약·회사 프로필 | 경로·위험도·도구·예산·기밀 범위 확인 |

`status: done`이어도 `hq: review`이면 관리자 확인이 남아 있습니다. 이를 숨기지 않는 HQ 행동 뷰를 사용합니다. 실제 경로는 회사의 로컬 프로필에 있습니다.

## 통제와-중단

- `중단: <작업>`으로 안전 지점에서 멈춥니다. Agent는 부분 결과·복구 지점·남은 실행과 자원 사용을 기록합니다.
- 목표·허용 오차·출판 주장·새 지출·쓰기 범위 확대는 관리자가 결정합니다. 구현 순서와 승인된 한도 안의 보완은 위임할 수 있습니다.
- 관리자가 부재하면 이미 승인된 범위만 계속합니다. 승인 대기 시간 경과는 승인이 아니며, 긴급하다는 이유만으로 기밀·외부 발신·원본 보존 규칙을 넘지 않습니다.
- 다음 세션은 원 증거·입력·승인·완료 단계를 다시 확인합니다. 감시 서비스가 없으면 자동으로 다시 시작한다고 약속하지 않습니다.

세부 값은 [제어 설정](Control_Settings_admin.md), 중단·재개 절차는 [작업 흐름](../AI/Workflow_agent.md#hq-판단과-재개)을 봅니다.

## 주간-운영

1. 프로젝트 STATUS에서 이번 주에 확인할 결과를 고릅니다. 마감·연구 가치·의존성·실제 자원으로 우선순위를 정합니다.
2. 진행 중 작업과 HQ 대기를 확인합니다. 프로젝트당 기본 실행 작업은 하나이고, 쓰기 범위가 겹치는 작업은 순서대로 실행합니다.
3. 반복 질문·검증 실패·재작업이 생긴 작업을 돌아봅니다. 필요한 개선은 기존 TaskNote나 Decisions에 기록합니다.
4. 한도를 바꾸려면 실제 사례와 영향을 근거로 결정합니다. 새 대시보드나 회고 문서를 의무적으로 만들지 않습니다.

## 규칙을-바꾸는-방법

공통 규칙은 프로토콜 저장소에서, 회사 경로·도구·기밀 목록은 로컬 프로필에서, 실제 적용 버전은 로컬 채택 기록에서 관리합니다. 저장소를 업데이트했다고 실행 중 작업의 승인 범위가 자동으로 바뀌지는 않습니다.

확장 모드를 도입하려면 [도입 모드](../Setup/README.md#도입-모드)의 구현·시험 조건을 충족하고 관리자가 활성화를 지시합니다. 프로토콜 문서를 승인했다는 사실과 프로그램이 실행 가능하다는 사실은 구분합니다.
